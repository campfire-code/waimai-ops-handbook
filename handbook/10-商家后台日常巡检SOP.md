# 商家后台日常巡检 SOP

> 本章整理的是一套通用的「商家后台每日巡检与数据核对」做法。后台菜单名称、入口和字段会随平台版本变化，**一律以平台当前后台为准**；这里的入口名称只用于说明流程。

## 一、先分清两件事：读和写

- **读**：看订单、商品、评价、财务等数据。风险低，是巡检的主体；
- **写**：接单、改价、改库存、上下架、回复评价、提交申诉、启停活动等。会改变经营状态，风险高。

**原则：生产账号默认只读。** 任何写操作，必须按本章第四节的流程先在测试条件下验证。

## 二、日常工作流地图

| 工作流 | 看什么 | 典型输出 |
|---|---|---|
| 订单监控 | 日期、订单类型、履约状态 | 待接单、待出餐、配送中、已完成 |
| 接单履约 | 订单详情 | 接单、出餐、骑手状态 |
| 商品库存 | 状态、分组、规格、库存、价格 | 在售、售罄、下架、违规 |
| 营业配送 | 营业状态、配送时段、配送范围 | 营业与配送状态 |
| 顾客消息 | 未回复、未读、会话分类 | 会话与平台通知 |
| 退款售后 | 退款、餐损、食安状态 | 待处理项、申诉进度 |
| 营销推广 | 活动类型、状态、时间 | 活动数据、投产比、推广状态 |
| 评价口碑 | 星级、回复状态、差评关键词 | 评分、评价、趋势 |
| 财务对账 | 日期、交易类型、订单状态 | 订单明细、账单、收入 |

### 建议的巡检顺序

```text
确认当前门店
  -> 订单与履约
  -> 商品库存
  -> 营业与配送
  -> 顾客消息
  -> 退款售后
  -> 营销活动
  -> 评价口碑
  -> 财务对账
  -> 回到起点页面
  -> 确认本次巡检没有产生任何经营写入
```

## 三、多门店作业

同一个总账号下，不同门店的数据、入口甚至页面布局可能不同，**不能拿一家门店的页面当作所有门店的模板**。

### 标准流程

1. 记录当前门店的标识和状态；
2. 打开门店选择器，选择目标门店；
3. **验证门店确实已经切换**，再开始操作；
4. 从统一的安全起点页面开始；
5. 先识别当前页面的布局类型，再按类型读取，而不是只匹配一个固定标题；
6. 保存结果；
7. 回到门店选择器，恢复到原来的门店；
8. 再次确认回到了原门店和起点页面。

### 实用经验

- 不同门店的快捷入口位置可能不同，不要硬编码点击位置；
- 页面可能保留上一次打开的标签，开始前要主动选择正确的标签；
- 门店很多时，先按状态（营业中、停业、已下线等）选取有代表性的门店，找出异常后，再对异常门店深读；
- 门店数量是时间快照，不要写成永久常量。

### 失败恢复

- 前台不是预期的应用：停止，不要跨应用点击；
- 页面特征不足：回到起点页重试一次；
- 门店切换失败：不继续，恢复原门店；
- 原门店没能恢复：任务算失败，不要报「完成」；
- 发现任何经营状态发生了变化：立即停止，保留记录。

## 四、受控的写操作

### 前置条件

必须同时具备：测试门店、测试订单、测试商品、明确允许的操作、可验证的预期结果。**缺任何一项，只能识别界面和做计划，不能提交。**

### 每个写操作的四段校验

```text
准入校验 -> 目标绑定 -> 提交前预览 -> 提交后读取验证
```

| 阶段 | 要做什么 |
|---|---|
| 准入校验 | 当前是否为测试门店；目标是否为测试订单或商品；账号是否有权限；有没有未处理的弹窗 |
| 目标绑定 | 用匿名标识绑定目标；页面显示值要与测试配置一致；找不到唯一目标就停止 |
| 提交前预览 | 记录变更前的值；展示变更后的值和影响对象数；高风险操作必须人工确认 |
| 提交后验证 | 重新读取页面核对结果；保存证据；能回滚的操作要验证恢复路径 |

### 禁止事项

- 不用真实顾客的退款做测试；
- 不用真实在售商品做改价测试；
- 不批量操作没有绑定的商品；
- 不自动发送带承诺、赔付或争议内容的消息；
- 不把测试凭证、订单号、账号信息提交到公开的代码仓库。

### 推荐验证顺序

先低风险、可恢复的配置类操作，再到订单履约、退款、营销、财务等高风险操作。

## 五、数据完整性核对

「页面看过了」不等于「数据完整了」。每轮采集后，用下面的规则核对：

1. **数量闭合**：页面显示的总数，必须与你整理出的记录数一致；
2. **汇总与明细闭合**：例如分组商品数之和，要等于商品总数；
3. **到底才算完**：列表要滚动到稳定的底部，并确认没有后续加载；
4. **不要把角标当总数**：页面上的待处理角标可能和实际加载的列表不一致，发现差额就如实报告，不要硬凑；
5. **序号不是主键**：页面上的 `#序号` 可能重复或跳号，不能用「日期 + 序号」去重，要用订单号等稳定标识，或者「日期 + 序号 + 时间」的组合；
6. **账期口径**：财务页面按平台账期展示，账期可能跨自然月，不能看到月份变化就停止；
7. **重复导入新增为 0**：同一批数据导入第二次，不应增加记录（幂等）；
8. **不跨门店合并**：不同门店的数据分开保存，不要混在一起；
9. **同一秒的多条记录**：批量操作可能在同一秒产生多条不同的记录，去重不能只用「时间 + 类型」。

## 六、几个只读场景的边界

### 售后与申诉

- 待处理申诉数大于 0，说明有待办，**不等于**商家已经提交了申诉；
- 「未申诉、不可申诉、顾客的退款申请、餐损申请、普通退款进度」都不能算作已提交的申诉；
- 只读检查时，不打开待申诉的个案、不进入申诉表单、不上传凭证、不处理退款、不联系顾客。

### 消息

- 为了测试而打开未读消息，会把未读变成已读，影响经营。**有未读标记时不要打开**；
- 空状态只能证明入口存在，不能代表其他门店也一样；
- 没有合适的无副作用样本时，不要为了测试去逐店打开生产的消息页面。

### 评价与财务

- 评价的回复、修改回复、申诉、联系顾客、发券，属于写操作，只读巡检时不要触碰；
- 财务只读，不要提现、转账、下载或导出，也不要改变筛选条件。

- [ ] 列表已滚动到底，总数与记录数一致
- [ ] 没有把角标或页面序号当总数或主键
- [ ] 重复导入新增为 0
- [ ] 已恢复原门店和起点页面
- [ ] 异常已记录，没有为了凑数而补写数据
